# 小格自然对话与知识库产品咨询整改方案

日期：2026-10-20。状态：**设计及交接方案，未实施、未复测，不构成 READY。**

用户已明确：客户不会按模板提问；当前产品咨询应以客户知识库的数据为依据，支持“介绍产品 → 看参数 → 按该参数找其他产品”的连续咨询。另有任务正在修改 Backend/App，因此本轮只新增本方案，不修改其运行代码、不部署、不写业务数据。本方案不是要求另建一套大架构。

已确认的线上断点及证据见 [四组真实对话审计](conversation-integrity-audit-2026-10-20.md)。以下区分已证实缺陷、目标行为和建议实现；不将尚未完成的设计写成已修复结果。

## 一、修复目标不是猜中每一种问法

自由表达由 DeepSeek 理解；Backend 维护持续的业务需求、绑定实际对象并执行查询。允许客户省略、改口、使用简称、打错字、插问概念或换话题，不要求客户理解产品编码、指标字段或后端流程。

无法唯一理解时，只问影响下一步的真实歧义。正确处理不确定性也是通过：不能为了给出结果而丢条件、补工程参数、扩大查询范围或绑定一个未经确认的对象。

保留现有 Knowledge、Thermal Engine、候选/Final/Confirm、Snapshot 与 PDF；整改集中在语义提案、上下文合并、读取合同和回答组织的连接处。

## 二、知识库是产品咨询依据，但必须保留数据归属

### 2.1 产品咨询的资料范围

- 读取客户当前有权访问、已发布、生效且允许 AI 使用的知识资料；热工表使用已确认快照，普通介绍使用可核验的正文段落和资料页。
- 产品目录、已发布规格作为已经核验的补充。不能因目录只有一条就说客户只有一款产品，也不能要求资料里每个可介绍对象先有 SKU 才能只读介绍。
- 问产品全集时，说明“目前这份知识资料收录/能查到的范围”，不能把可见资料范围说成客户全部商业产品。
- 知识资料中的产品、规格、系统、构造方案与材料层分别标记。构造表标题不一定是产品名称；在某个构造里出现的板厚，不一定是产品完整供货规格。
- 知识库与目录冲突时，展示各自来源、版本和口径，区分真正冲突与不同对象，不静默选一个值。缺少正式依据时不作工程推荐。

### 2.2 从“搜索到文字”补到“可查询的关系”

需要复用现有确认模型和来源绑定，提供只读的产品事实视图；不要求引入图数据库，也不改写原资料、发布规则或历史快照。

| 内容 | 必须保留的关系 |
| --- | --- |
| 名称与称呼 | 原文名称、对象类型、正式别名/已确认映射；未确认近似称呼只用于建议 |
| 产品介绍 | 对应产品及支持该描述的正文片段、适用条件；不从表头臆测用途、优势、认证 |
| 参数 | 对象、参数名称、数值、单位、口径、适用规格/厚度/构造条件 |
| 来源 | 文档、版本、页身份、可见页码、确认 Revision；适用时绑定构造、档位、层或正文片段 |
| 完整性 | 已覆盖的资料范围、缺项、原值疑点及冲突状态 |

例如，同为 λ，产品当量、规格标称与芯材/构造材料层的值不能互换；产品热阻也不能替换为整构造总热阻。跨产品筛选只能在明确且一致的参数口径下进行。

现有工作区已增加按标题和材料层名称归纳产品线索的读取。这可用于发现资料，不能单凭标题括号、名称关键词、出现页数认定产品身份、参数归属或完整系列覆盖。产品身份有歧义就保持未确认；资料中的局部对象可带来源只读介绍，不自动升级为正式候选。

## 三、服务端保存一份有效需求，模型只提出本轮变更

优先扩展现有会话状态，不新增互相竞争的“最近一次查询”副本。逻辑上区分以下三类信息，但归属同一条有效需求和消息链：

| 状态 | 内容 |
| --- | --- |
| 当前需求 | 目标、对象/名称线索、筛选条件、比较符、数值/单位、口径、来源范围；每项标记来自哪条用户消息或哪次明确选择 |
| 待补充信息 | 缺哪项、为什么需要、关联原问及澄清消息、已经给出的候选建议；不靠回找最近一个数字恢复 |
| 当前谈论对象与事实 | 用户当前关注的产品/构造、最近实际展示的结果集合、参数焦点、可回溯来源；不是整段回答文本的任意猜测 |

DeepSeek 继续使用已支持的 JSON-object 输出，提出本轮操作和证据，例如补充指标、修改阈值、选择对象、解释参数、撤销条件、开启新话题。Backend 完成结构/字段/证据校验和状态合并；正式 ID 只能从当前有权对象中绑定，不能由模型补写。

不能以模型没有输出 `CLARIFICATION_REPLY` 为由放弃正在等待的原查询。若本轮提案与活动需求不一致，先做上下文一致性判断；需要时沿用现有同预算有限复核，不能直接执行被拓宽的查询。也不能反过来强行把所有短句当成续问。

### 状态合并规则

1. **补充**只填缺项；“导热系数”补指标，不抹掉原先“小于 0.35”、名称线索及“找方案”的目标。
2. **修改**只改用户明确修改的部分；更换指标时检查旧数值是否仍适用，不将 K 的阈值直接套给 λ。
3. **解释插问**不授权计算或确认。问“热阻是什么意思”可以解释，并保留尚未完成的需求；不能一概视为补充热阻指标。
4. **反向查找**先绑定参数焦点，再区分用户是想看其他产品的该指标、找相同数值，还是沿用原筛选范围。只有有证据的数值/范围才成为筛选条件，不能把“也有这个参数”一律改成等值查询。同时按用户“其他产品”的意思解除原产品身份限制；保留口径及其他仍适用条件。这是有证据的目标变更，不是静默宽查。
5. **歧义**保留已知条件，只问缺项。同一轮有多个参数时，“这个参数”不能随意选一个；多个方案时，“那个”不能绑定任意后台 ID。
6. **新话题、取消与返回旧话题**由明确话语和有效上下文判断。不能因历史存在某个数字、旧建议或“好的”就复用旧选择，更不能把旧上下文当副作用授权。
7. 每次使用上下文都重验本人、客户端、会话、项目、有效期及当前资料版本/Revision；并发请求按现有会话串行/版本机制避免相互覆盖。失效时说明需要重新读取，不静默沿用。

## 四、产品连续咨询应如何表现

以下只展示交互要求，不代表知识库实际具备示例所述内容，也不提供虚构工程值。

| 用户说法 | 后端应维持的上下文 | 客户应得到的帮助 |
| --- | --- | --- |
| 介绍一下 XXX | 已定位或待确认的资料对象、来源和产品介绍目标 | 用资料支持的内容介绍它是什么、特点/适用范围；有哪项就讲哪项，不默认倾倒所有热工值 |
| 这个产品有什么参数 | 继承已唯一定位的 XXX；目标切换为参数概览 | 展示已确认的主要参数和单位，必要时区分规格；附可打开的来源，不重新问产品名称 |
| 这个导热系数是什么意思 | 保持 XXX 与所问 λ 的口径，目标为解释 | 解释该参数和资料中的含义，不自行比较优劣或承诺工程效果 |
| 这个参数还有哪些产品 | 绑定唯一指标焦点和口径，识别是看其他产品的该参数、同值筛选还是延续原范围；不自动等值 | 能确定就查同口径其他产品；上轮有多个指标则问所指指标，若“看该参数”与“同值找产品”仍有实质歧义则只澄清这个区别 |
| 想找更低一点的 | 继承唯一指标和参照值；明确比较对象和方向 | 查同口径低于该值的产品；“更好”没有明确评价依据时先问关注点 |
| 第二个呢 / 这两个对比一下 | 绑定用户实际看见的结果集合及来源 Revision | 唯一绑定后读详情或对比；产品咨询结果不能自动当作可 Confirm 的正式方案 |
| 不看这个了，介绍 YYY | 开启新对象，清除不适用的旧产品条件 | 介绍 YYY，不能把 XXX 的厚度、参数或构造筛选带过去 |

“有哪些同参数产品”应先说明正在沿用的参数/口径；参数名称与参数数值是两回事。明确“同样的数值”才做同值匹配，明确“也看下其他产品的这个参数”则查询该指标；精确、范围与容差遵循用户语义和现有正式匹配规则。不能暗加容差或用“差不多”擅自扩展工程范围。

## 五、执行前后都验证业务条件

### 查询前

- 比较有效需求与最终 QuerySpec：目标对象、名称线索、指标、比较符、值/单位、口径和来源约束不能无故消失。
- 约束可以由用户明确解除、修改或随新话题失效；必须记录原因和证据，不能机械禁止合理的跨产品查询。
- 未解析名称不能变成 ANY 后查全库；“找方案”也不能改成列出材料层。若 λ 无法直接筛整套方案，说明需要确认哪个产品/层的 λ，保留原阈值。
- 未带数值的合法参数概览、独立全量阅读仍可执行；保护应基于活动需求的真实约束，而不是统一禁止 READ。

### 查询后

- 所有正式匹配结果必须满足实际数值条件及对象口径。显示前若发现不一致，停止这次结果输出并记录断点，不能靠截断/去重掩盖。
- 区分“名称未对应”“可核验资料里没有该参数”“筛选后无命中”“资料冲突/疑点”“检索服务异常”。错误不伪装成资料缺失。
- 总数、分页和去重语义明确；仅统计相同对象口径下的实际命中，不能用原始层数充当产品数或方案数。
- 对缺口自然说明，并提供可做的下一步；不要求用户补出本次根本没指定、也不影响只读查询的全部工程条件。

## 六、事实严格，表达自然

Service 负责返回结构化事实、可核验描述片段、真实缺项和来源；回答层按本轮目标组织简洁语言，表格/卡片直接消费同一份结构化数据。

模型不能自由补工程事实。回答校验需要将每个数值及结论绑定到对应对象、属性、口径和来源，而不是只检查“这个数字是否曾在全部事实里出现”。定性用途/性能/认证同样需要资料支持；缺资料不补宣传话术。

产品介绍不再由 SUMMARY/CATEGORY 等字段固定拼句决定全部表达。介绍、概览、追问解释、无命中说明都可自然组织，约束来自事实而不是固定客服台词。用户只问一个参数时先答该参数，不附大段内部合规说明。

工程表格仍复用来源数据及客户表头显示投影，包含原值和疑点标注；不交给模型重新拼数值。A2-2、A3-3 已确认资料疑点继续原值保留。候选/确认/报告权限和 Snapshot 冻结规则全部保留。

## 七、最小范围实施顺序及现有模块对应

以下是交接建议，不是本轮改动清单；实际代码以另一任务收敛后的版本重新核对。

| 顺序 | 工作 | 优先复用/核对的位置 | 完成标准 |
| --- | --- | --- | --- |
| 1 | 统一活动需求、待澄清链和变更合并 | conversation-task、query-clarification-context、ai-domain-turn-decision、ai-domain-policy | 补充信息不会重建并丢失旧条件；换话题不带入旧条件；不依赖单个模型标签 |
| 2 | 查询前后约束检查及分型诊断 | product-parameter-query/read、reference-query、统一只读读取及 diagnostics | G2 不再宽查，G3 能指出名称问题，G4 保留目标并只问真实缺项 |
| 3 | 知识库产品事实与参数焦点 | product-read、product-consultation-context、confirmed-page-facts、knowledge 现有正文检索 | 可据资料介绍对象、看参数、解释与同口径反查；来源/口径可追溯 |
| 4 | 自然回答与 C 端一致展示 | product-answer/answer-plan、ai-generation、App 消息/表格/卡片契约 | 回答与卡片来自同份结果，按客户问题给帮助，不固定套话或串对象参数 |
| 5 | 真实复测及整体回归 | 现有隔离 H5、DeepSeek HTTP/SSE 与原35问工具 | 证据链通过且关键业务/权限不回归后才评估 READY |

先采用现有确认数据的只读视图，不先建设新的产品主数据系统或做全量物化迁移。若知识库缺少足以确定产品归属的字段，列明具体资料缺口；不得为了实现连续咨询伪造映射。

## 八、验收方法改变，原35问保留

当前仍按用户要求暂停扩展测试场景，先处理四组现有失败会话。另一任务收敛后，在隔离环境用真实 DeepSeek + 真实 H5 复测，采集并对照：

`用户原话 → 合并前状态 → 模型提案及证据 → 状态变更/缺项 → 最终 QuerySpec → Service 参数/结果 → 来源 → 回答/卡片`

除业务内容外，记录代码、Prompt/模型配置及来源版本；敏感信息脱敏。若原始提案未采集，明确标缺失，不能事后推测补齐。

四组先验收：G1 按知识资料范围给有帮助的介绍；G2 保留小于阈值与方案目标且不返回越界混合材料；G3 保留 K 条件并处理未确认名称；G4 保留原数值并只澄清必要的 R 口径。随后原35问逐字重跑、完整候选到 PDF 链路及关键权限回归。

这一轮通过后，再采用与修复实现分离的自然问法盲测方法：围绕同一个业务目标改写、补充/撤回条件、插问概念、换话题并返回、引用多个对象。评判依据是用户需求、最终执行条件和资料事实，不能照抄代码输出当预期。不是不断扩充固定句子的特判库。

必须检查四件事：已明确的有效条件是否无故丢失；实际结果是否全部符合事实与口径；是否反复澄清已知内容；未预设的问法是否仍能合理推进或准确说明歧义。计算、Snapshot、Confirm 和 PDF 单独检查权限与数据一致性。

不能承诺任意奇怪问题都一次理解正确；必须做到不能确定就准确接话，已经确定的条件可靠保留，最终执行和回答都有依据。现阶段不能恢复整体 READY。
