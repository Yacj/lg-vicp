# 蓝格 VICP 后端：Wiki 层级知识体系 + 甲方 P0/P1 增量改造计划

## 一、现状审计结论（现状 → 改动点 → 影响范围）

**已存在（不重复实现）：**
- `knowledge_sections`（schema.ts:651）、`knowledge_page_blocks`（:701）、`knowledge_pages`（含 pageNumber/parsedText/sectionPath/pageImageObjectKey）、`knowledge_chunks`（含 sectionId/pageBlockId/keywords/citationAnchor/contentType）表**均已在 schema 中定义，且解析 Worker `writeParsedContent`（document.worker.ts:403-472）已按 版本删旧重写 6 张表：sections → pages → page_blocks → chunks → chunk_terms → citations**。标题/表格块/锚点/关键词均已提取；`handleChunkRebuild`（:563）复用 `writeParsedContent`，即"从页面原文重建完整 Wiki 层"的回填能力已内建。
- `thermal_calc_records` 已存 stepsJson（key/label/value/rounded/formula）+ layersJson（layerOrder/layerName/lambda/correctionFactor/证据）+ resultJson + standardJson；CalcStep 标签为中文，可直接派生人读展示。
- 候选查询 schema 已有 `systemId`（保温体系）条件；候选确认/计算/候选查询 AI 端 3 条路由已存在。
- 标准 CRAWL/MANUAL 双通道 → 审核 → 指标 publish 同事务写 `thermal_standard_limits` 链路完整（standard.service.ts:667-727）；`md-workflow` 状态机、`md-read.service`（PUBLISHED+生效区间口径）、`construction-read.listPublishedInsulationSystems` 可直接复用。
- `shared/client-guard.ts` 已有 `requireClient()` preHandler；`roles.dataScope` 枚举已存在（ALL/DEPT/DEPT_AND_CHILDREN/SELF/CUSTOM/PROJECT_OWNER）；`users.channelType` 已有。

**确认的问题/缺口（本轮改动点）：**
1. **schema 与迁移漂移**：sections/page_blocks/chunks.section_id/page_block_id/pages.section_id 等从未进过任何 drizzle 迁移（最新 0024）。必须先 `db:generate` 补齐并人工审查 SQL。
2. 检索主流程 `runSearch` 只查 `knowledge_chunks`；sections/blocks 未参与检索；`RetrievedKnowledgeChunk` 的 sectionId/pageId/pageBlockId/headingPath/pageContext 预留字段从未赋值。
3. `searchProjectKnowledge` 过滤 `kc.project_id = X`，**平台级文档（projectId 为空）对 AI 会话完全不可见**——体系驱动检索必须放宽为"项目文档 + 平台文档"。
4. regenerate 的 sources 只有 `{title,page}`（ai.routes.ts:1026），与正常生成（ai-generation.service.ts:373-381）不同构；docs/ai/sse-protocol.md:44 文档也落后。
5. `ai_conversations` 无 insulationSystemId；无体系必选/切换逻辑。
6. `sortCandidates` 未按 targetK-kValue 升序（matcher:201-210）。
7. `knowledge_documents` 无 visibility、无体系标注列；无 C 端只读知识/企业内容接口。
8. 无 notifications 表/模块；`users` 无 channelId/parentChannelId；抓取源缺运营回写字段。
9. block 的 startOffset/endOffset 列存在但写入时未填充 → 高亮 charStart/charEnd 需在读取服务中按 block 文本在页全文中定位（block 文本是页面原文逐行提取，可稳定 indexOf 命中）。

## 二、实施步骤

### P0-0 Wiki 层级检索改造
1. 先改 schema 再生成迁移（合并漂移补齐）：`knowledge_sections` 增加 `searchText`（trgm 索引）；`knowledge_documents` 增加 `visibility`（varchar，PUBLIC/PRIVATE，默认 PRIVATE）与 `insulationSystemId`（uuid nullable → insulation_systems）。
2. Worker `buildWikiStructure`/写库处填充 sections.searchText（标题 + headingPath 链）；文档入库链路透传 visibility/insulationSystemId（knowledge-ingest + admin service + DTO/schema）。
3. 新增 `src/modules/knowledge/knowledge-wiki-read.service.ts`（统一 Wiki 读取服务）：已发布版本校验、文档详情+章节树、页面列表/单页（fullText+blocks）、来源定位解析（sectionId/pageId/blockId/chunkId → 文档+章节路径+页+块）、高亮定位（blockId 优先，matchedText indexOf 兜底，读时计算 charStart/charEnd）。P0-2 与 P0-6 共用，不写两套。
4. `knowledge.service.ts` 新增 `searchWikiHierarchy(app, query, options)`：options `{projectId?, docType?, categoryId?, region?, purpose?, insulationSystemId?, visibility?: 'PUBLIC', limit}`。层级：① sections（searchText/标题/条款号，复用权重规则）→ ② page_blocks（trgm）→ ③ chunks（现有 runSearch 辅助召回）；按 sectionId/pageId 聚合去重，hit 标 `retrievalUnit`（SECTION/PAGE/BLOCK/CHUNK）；节内全部 blocks ≤2000 字时整节作 content（小文件整节入上下文），否则命中块内容 + pageContext。体系联动：文档 insulationSystemId 标注列强加权/优先，未标注文档仍可召回兜底；体系名称/编码关键词加分。
5. `searchProjectKnowledge` 改为 `(app, projectId | null, query, options?)`，项目口径放宽为 `(project_id = X or project_id is null)`，回填全部预留字段 + retrievalUnit；调用点 3 处（ai-generation.service.ts:168、ai.routes.ts:818/:1133）同步。`formatKnowledgeContext` 输出章节路径与检索单位。
6. 回填脚本 `scripts/backfill-knowledge-wiki.ts`：对"有 pages 但无 sections/blocks"的已解析版本逐个执行 writeParsedContent 同构重建（或投递 CHUNK_REBUILD），支持 --dry-run；历史资料允许用现有 reparse/chunks/rebuild 端点逐步升级，不做全量强制重跑。

### P0-2 来源详情 Client API

### P0-3 会话保温体系
- 迁移：`ai_conversations.insulation_system_id` uuid nullable → insulation_systems（restrict）。
- 新错误码 `AI_INSULATION_SYSTEM_REQUIRED`（ai-errors.ts，400 语义）。
